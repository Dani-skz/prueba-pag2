Automatización de procesos con GitHub Actions y runners de Linux

Cómo GitHub Actions automatiza tareas de un proyecto y cómo Linux las ejecuta mediante comandos y procesos.

1¿Por qué existe la automatización?

Cuando programamos, cambiamos el código todo el tiempo y cada cambio puede romper algo que antes funcionaba. Comprobarlo a mano cada vez es lento y propenso a errores. Por eso existen dos ideas:

Integración continua (CI)Integra los cambios al código y comprueba automáticamente que no haya errores.
Despliegue continuo (CD)Prepara o publica automáticamente una versión del programa.

2¿Qué es GitHub Actions?

Es una herramienta de GitHub que automatiza tareas dentro de un proyecto. Por ejemplo, cada vez que alguien sube cambios con git push (enviar los commits locales al repositorio remoto), se ejecutan pruebas automáticamente. Esa automatización se llama workflow y tiene cuatro elementos:

EventLo que dispara el workflow (por ejemplo, un push).
RunnerLa máquina que ejecuta las tareas.
JobConjunto de steps que corren en un mismo runner.
StepsLos pasos individuales dentro de un job.

Los steps de un job se ejecutan en orden. Los jobs pueden correr en paralelo o depender unos de otros.

Ejemplo de workflow (se escribe en un archivo YAML dentro del repositorio):

on: push                      # event
jobs:
  test:                       # job
    runs-on: ubuntu-latest    # runner (Linux)
    steps:                    # steps
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm test

3El runner de Linux

El runner es el entorno donde se ejecutan las tareas del workflow. Puede ser Linux, Windows o macOS, y puede ser una máquina que provee GitHub (como ubuntu-latest) o una propia.

Linux es muy usado porque permite ejecutar comandos, scripts y herramientas para instalar dependencias, ejecutar pruebas, compilar el programa y generar archivos.

GitHub Actions organiza y solicita las tareas; el runner las ejecuta.

4Procesos en Linux

Cuando Linux ejecuta un comando o programa, crea un proceso: un programa en ejecución. Cada proceso tiene un identificador único, el PID, que permite reconocerlo y administrarlo. Cada run: de un workflow (como npm test) se convierte en un proceso dentro del runner.

ComandoFunción
psMuestra información de los procesos.
htopPermite observar y administrar procesos de forma interactiva.
killEnvía señales a un proceso para pedirle que termine u otra acción.

Si un programa se traba, identificamos su PID y le enviamos una señal para finalizarlo.

Estados de un proceso:

EstadoSignificado
RunningSe está ejecutando o está listo para ejecutarse.
SleepingEspera un evento o un recurso.
StoppedEstá detenido.
ZombieTerminó, pero su proceso padre todavía no recogió su estado de finalización.

5¿Cómo se relaciona todo?

Desarrollador sube cambios al repositorio de GitHub
↓
GitHub Actions detecta el evento y activa el workflow
↓
Runner de Linux recibe y ejecuta los jobs y steps
↓
Procesos de Linux ejecutan comandos, pruebas y programas
↓
Resultado la automatización termina y se informa si tuvo éxito o falló

Al terminar, cada proceso devuelve un código de salida: si es 0, el step salió bien; si es distinto de 0, el step falla y el workflow se marca como fallido. Así GitHub informa el resultado.

GitHub Actions define cuándo y qué ejecutar; el runner proporciona el entorno; Linux administra los procesos que hacen el trabajo.
