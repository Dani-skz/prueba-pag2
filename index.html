GitHub Actions y procesos de Linux

Cómo GitHub Actions automatiza las tareas de un proyecto y cómo Linux las ejecuta mediante comandos y procesos.

Comenzar
01 · Introducción

¿Por qué existe la automatización?

Cuando programamos, cambiamos el código todo el tiempo, y cada cambio puede romper algo que antes funcionaba. Comprobarlo a mano cada vez es lento y propenso a errores.

Integración continua (CI)

Integra los cambios al código y comprueba automáticamente que no haya errores.

Despliegue continuo (CD)

Prepara o publica automáticamente una versión del programa.

Ambas buscan automatizar tareas que normalmente haríamos de forma manual.

02 · GitHub Actions

¿Qué es GitHub Actions?

Es una herramienta de GitHub que automatiza tareas dentro de un proyecto. Por ejemplo, cada vez que un desarrollador sube cambios con git push, se ejecutan pruebas automáticamente. Esa automatización se llama workflow y tiene cuatro elementos:

I

Event

Lo que dispara el workflow, por ejemplo un push.

II

Runner

La máquina que ejecuta las tareas.

III

Job

Conjunto de steps que corren en un mismo runner.

IV

Steps

Los pasos individuales dentro de un job.

Los steps de un mismo job se ejecutan en orden. Los jobs pueden correr en paralelo o depender unos de otros.

# .github/workflows/test.yml
on: push                      # event
jobs:
  test:                       # job
    runs-on: ubuntu-latest    # runner (Linux)
    steps:                    # steps
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm test
03 · Runner

El runner de Linux

El runner es el entorno o máquina donde GitHub Actions ejecuta las tareas del workflow. Puede usar Linux, Windows o macOS, y puede ser una máquina que provee GitHub (como ubuntu-latest) o una propia.

Linux es muy usado porque permite ejecutar comandos, scripts y herramientas para instalar dependencias, ejecutar pruebas, compilar el programa y generar archivos.

GitHub Actions organiza y solicita las tareas; el runner las ejecuta.
04 · Procesos

Procesos en Linux

Cuando Linux ejecuta un programa o comando, crea un proceso: un programa en ejecución. Cada proceso tiene un identificador único llamado PID, que permite reconocerlo y administrarlo. Cada run: de un workflow, como npm test, se convierte en un proceso dentro del runner.

ComandoFunción
psMuestra información de los procesos.
htopPermite observar y administrar procesos de forma interactiva.
killEnvía señales a un proceso para solicitar su finalización u otra acción.

Si un programa queda trabado, podemos identificar su PID y enviarle una señal para finalizarlo.

Estados de un proceso

EstadoSignificado
RunningEstá ejecutándose o listo para ejecutarse.
SleepingEstá esperando algún evento o recurso.
StoppedEstá detenido.
ZombieTerminó, pero su proceso padre todavía no recogió su estado de finalización.
05 · Relación

¿Cómo se relaciona todo?

  1. Desarrollador
    Sube cambios al repositorio de GitHub.
  2. GitHub Actions
    Detecta el evento y activa el workflow.
  3. Runner de Linux
    Recibe y ejecuta los jobs y steps.
  4. Procesos de Linux
    Ejecutan comandos, pruebas y programas.
  5. Resultado
    La automatización termina y se informa si tuvo éxito o falló.

Al terminar, cada proceso devuelve un código de salida: si es 0, el step salió bien; si es distinto de 0, el step falla y el workflow se marca como fallido.

06 · Resumen

Para recordar

GitHub Actions define cuándo y qué ejecutar; el runner proporciona el entorno; Linux administra los procesos necesarios para realizar esas tareas.
